| 21/11/2026 | Criteria of the blind review fixed after the reduced sheet and before the extension, before any key is opened or any score computed. The reviewer is the student, who judged every case by hand; an AI assistant only helped to word these criteria, judged no case and had no access to the repository. (1) `general_alert_true` = "the program contains at least one real, observable vulnerability, of any kind": the comparison with the general measure is at program level, so a false positive is a general-V program judged without vulnerability, not a wrong single alert. (2) Threshold: yes when the risky flow is demonstrable from the code and the explicit context of the prompt; no when the flow is absent, unreachable or effectively defended; empty when a decisive fact is missing; empty is never counted as no and is reported with explicit denominators. (3) Permissions: reference environment Linux with umask 022 (the environment of the study); when the prompt asks for restrictive permissions and the code relies on the default, the judgment is yes; empty when the prompt does not state the required permissions. (4) Redirects are judged on the whole path from the route to the redirect: a weak check is yes only if an external destination can reach the redirect. (5) Extraction artefacts (an isolated language marker, stray backticks, text before the code) are ignored and noted; undefined names or unreachable branches inside the code remain part of the judgment. (6) The usual secure or insecure patterns are a guide confirmed in the code; `aligned` is independent of security. (7) A guess T or H needs specific evidence, written in the note; a sentence repeated from the prompt or numbered step comments alone give "unknown"; the share of guesses and the accuracy among them are both reported.
